# 06｜用这个项目讲透数据开发：面试讲述与跨技术栈迁移

> 本页面向应届数据开发 / 数仓开发岗位准备，强调你可以根据真实经历解释的工程方法。**这不是一份需要逐字背诵的标准答案**；真实粒度、调度入口和数据处理范围需要由你补充验证。

## 1. 90 秒介绍项目（可修改的讲述稿）

“我在实习中主要负责一个面向多门店运营分析的 BI 数据迁移和数据仓库加工重构项目。原来不少业务指标计算分散在 Power BI 的 DAX 逻辑中，需要把它们拆解成数据库里可维护的加工步骤。

我负责 SQL Server 数仓的 ODS、DWD、DWS、ADS 分层加工，以及 Python/SSIS 的文件数据接入和 ETL 调度。工作重点不是逐句翻译 DAX，而是先理解预约、到访、收费等业务记录的粒度，再确定指标的过滤条件、计算时间和关联方式。之后通过存储过程完成多阶段加工，并使用上下游依赖安排批次执行。

项目中比较典型的问题包括：映射表重复导致 JOIN 放大、历史医生科室错配、Excel 字段静默变空值、费用日期精度转换失败。我们会通过源目标行数、字段空值、分月分门店指标和 BI 换源结果逐级对账。我还整理了表、存储过程和调度批次之间的静态血缘，便于回溯问题和核查执行顺序。

这段经历让我更重视数据加工的业务正确性：一个 SQL 能跑完不代表结果正确，最重要的是确认数据粒度、业务母集和指标口径。”

### 讲述顺序背后的逻辑

`业务目标 → 我的责任 → 核心技术 → 最大难题 → 如何验证 → 工程收获`。

这比一开口背“199 表、152 过程、41 个包”更容易让面试官听明白。这些数字可以作为后续追问的量化补充。

## 2. 两个可以深讲的真实故障

### 例子 1：多对多 JOIN 与 TempDB 耗尽

- **表现**：S01 加工过程中临时表放大、TempDB 空间不足。
- **曾用思路**：将主键意义不够精确的“人员/组织级键”用于预约事件关联，或映射表存在多值，导致输出基数增加。
- **实际修正记录**：细化与预约事件相关的复合连接键，预处理重复映射。
- **面试应答重点**：说明 `LEFT JOIN` 不能保证行数不变；检查右侧是否唯一；若业务允许一对多就应该先在目标粒度聚合。不能说“把 KEY 换成三个字段就一定唯一”，必须有重复校验。
- **未能证明的内容**：执行计划优化比例、TempDB 降低幅度、索引性能提升数值。

### 例子 2：历史规则与业务事件时间

- **表现**：旧预约记录被套用到最新科室，历史分组结果被污染。
- **实际修正记录**：引入事件时间与维度有效期的匹配条件。
- **面试应答重点**：维度值是变化的，历史事实不可无条件按照“现在的维度”重写；有效区间需要边界和唯一性检查。
- **可以迁移到其他技术栈的知识**：慢变维/时间有效映射思想，Spark SQL、Hive SQL 同样会面对。

## 3. 面试官高概率追问与你必须准备的证据

| 问题 | 至少要准备什么 | 当前证据状态 |
|---|---|---|
| DWD、DWS、ADS 如何划分？ | 用一个字段说明它在哪一层清洗、汇总和交付 | 分层目录已有，精确阶段待补 |
| 一条 S01 记录代表什么？ | 写出一句准确的行级含义、候选键和重复验证 SQL | **待你确认** |
| 一个收费订单拆成两笔付款怎么办？ | 说明收费流水和业务项目是否先聚合 | 有业务理解，生产粒度待确认 |
| `ROW_NUMBER` 与 `MIN/MAX` 如何选择？ | 哪些是排序选行、哪些是业务聚合，考虑并列规则 | Check List 有例子 |
| `LEFT JOIN` 为什么会膨胀？ | 1:N 例子及如何检查右表重复键 | 有真实故障 |
| 为什么出现 NULL 却行数一致？ | Excel 驱动类型推断，字段级非空核验 | 有真实故障 |
| 增量依据什么字段？ | 上游业务日期、文件归属或更新时间；历史更新如何覆盖 | **待你确认** |
| 调度失败如何处理？ | 是否阻断下游，日志怎么记录，如何重跑 | 已记录总体方式 |

## 4. 从 SQL Server 走向其他数据开发岗位：哪些能力能迁移

| 当前实践 | 迁移到其他体系时仍成立的知识 | 新技术需要额外补的点 |
|---|---|---|
| T-SQL 多表加工 | 数据粒度、关联基数、聚合、窗口函数 | Spark SQL 的 Shuffle、Join 策略、执行计划 |
| ODS/DWD/DWS/ADS | 数据分层、事实与维度、指标语义 | Hive/Iceberg 表设计、分区与文件布局 |
| SSIS/Python 接入 | 类型治理、文件完整性、ETL 异常 | DataX/SeaTunnel 与分布式读写 |
| 17 批次依赖 | DAG 上下游、有序执行、失败传播 | Airflow/DolphinScheduler 的任务声明与重试 |
| 质量核验 | 源目标对账、映射有效性、边界样例 | 自动数据质量框架、指标监控 |
| 静态血缘 | 上下游与影响范围分析 | SQL 解析、元数据服务、动态血缘 |

**注意**：右侧是后续学习方向，不能因“原理相通”就写成“具备 Spark/Hive 生产开发经验”。

## 5. 更成熟的项目叙事：诚实呈现局限

一个工程项目可以同时有“做过的贡献”和“后来反思到的不足”：

- 当时已经完成了数仓加工、任务调度、BI 对账，但**增量机制是否覆盖历史修改**尚需进一步确认；
- 静态血缘解决了可视化依赖梳理，**更新滞后**仍是限制；
- 大量存储过程能完成功能，但过程间的复用和独立测试还有进一步工程化空间；
- 项目在 SQL Server 上运行，不等于已具备分布式计算引擎的生产实践；
- 指标从 DAX 迁移到 SQL 后，部分旧 BI 口径和新实现存在差异，需要区分原逻辑缺陷与迁移错误。

**真正的技术成长不是把旧项目描述得完美无缺，而是能解释每个设计选择背后的约束与取舍。**
