# 01｜业务拆解、粒度定义与数仓分层

> **文档属性**：源自《运营 BI 数据迁移分层明细》中的“分层明细”“SQL SERVER 命名规范”“SSIS 包命名”，并结合既有项目讨论。以下表名已进行抽象，未在原始工作簿中明确给出的粒度与具体阶段动作一律标注为待核对，不当作生产事实。

## 1. 从 BI 看板倒推指标加工

在传统 BI 逻辑中，同一份源明细上往往叠加了多套 DAX 计算列、度量值、映射和筛选逻辑。一旦需要迁移至 SQL Server，不能简单地逐行翻译公式。

正确的分析顺序：

1. **业务事件**：何时预约、是否到访、是否有收费，分别由哪种源数据代表？
2. **行级含义**：字段中的“患者、预约、项目、账单、付款”分别处于哪种粒度？
3. **过滤上下文**：按门店、日期、科室还是人员筛选？是否允许历史变更？
4. **聚合口径**：是否去重？最早/最近按什么排序？多笔支付是否都计入？
5. **时间归属**：按预约发生时间、业务日期还是付款时间入统计期？
6. **下游字段**：哪些结果提供给 ADS，哪些维度保留切片能力？

项目中最易出错的，就是第三、第四点。`MIN/MAX` 在 DAX 中所处的筛选上下文，不会因为写成 SQL 的 `MIN/MAX` 就自动保留；另外，先对明细 `JOIN` 还是先进行聚合，会改变业务含义。

## 2. 业务主题和数据流

从“分层明细”可观察到如下主题：

| 主题（匿名化） | 关注业务事实 | 关键映射/辅助数据 | 主要风险 |
|---|---|---|---|
| 运营与预约 OpsLine | 预约时间、到访、初复诊、组织科室 | 机构、预约项目、医生科室历史 | 同一对象多预约、最早/最近取值、科室有效期 |
| 费用与项目 BillingLine | 收费项目、支付时间、账单、金额、数量 | 收费项目及产品分类 | 一对多膨胀、金额精度与类型转换 |
| 汇总运营 OpsMerge | 历史/存量/增量运营合并 | 业务来源标识 | 历史范围和重复加载 |
| 预约/成交辅助 VisitAssist/DealAssist | 最早预约、最早成交、品牌与归类 | OpsLine/BillingLine 与映射规则 | 排序键、过滤字段错位 |
| 组织及业务维度 | 门店、科室、医生、来源等 | 组织/科室/项目等各类映射与维表 | 脏值、历史映射及重复键 |
| 其他业务主题 | 预算、渠道、产品消费、转介、手术、报销等 | 主题专属源与映射 | 多源融合及指标口径不一致 |

该表反映的是业务主题识别，不意味着已经建立严格的 Kimball 星型模型或所有表都设计了显式主外键；原始表清单里同时存在**映射表、桥表、事实表、静态表和汇总表**，以及因历史原因保留的特殊加工路径。表中主题名（OpsLine、BillingLine、OpsMerge、VisitAssist、DealAssist）为公开版泛化代号，非生产对象名。

## 3. 分层职责与实际路径

| 层次 | 责任 | 本项目可证实的工作 |
|---|---|---|
| **ODS** | 保存贴近上游的输入数据与必要接入清洗 | Excel 业务数据、映射表、历史/增量文件由 SSIS 或 Python 接入；个别日期、合并单元格和字段格式需要额外处理 |
| **DWD** | 统一字段、规范业务事件、处理映射/去重和明细计算 | OpsLine、BillingLine 多阶段加工；有关联、窗口函数、时间映射、业务过滤 |
| **DWS** | 面向主题的复用汇总或辅助加工 | 核心 OpsLine/BillingLine 主题表、最早预约/成交等辅助表存在 DWS 对象 |
| **ADS** | 面向 Power BI 的应用数据集与指标交付 | 主题报表结果、维度/映射及应用表；换源对账 |

实际分层明细目录记录的加工路径类别如下（目录记录行数，不是可运行任务数，也不等于最终物理表数量）：

| 加工路径类别 | 目录记录数 | 说明 |
|---|---:|---|
| `ODS→DWD` | 17 | 贴源数据进入明细加工 |
| `ODS→ADS` | 18 | 简单配置表直通交付层 |
| `DWD→ADS` | 36 | 明细结果直接供 BI 消费 |
| DWD 同层过滤/多阶段 | 36 | 同层内分阶段清洗与计算 |
| `DWD/ADS→DWS` | 5 | 少数历史遗留的跨层路径 |
| ADS 静态配置表 | 19 | ADS 层静态配置/字典表 |

其中 `DWD/ADS→DWS` 等跨层路径需要在未来的建模重构中评估是否产生循环依赖，但**不能凭架构图推断生产中存在循环**。

### 两条核心链路的建模关注点

**OpsLine（运营/预约）**

- 建议对每张关键中间表标注粒度，如“每条预约事件一行”；这是一种**复盘方法**，并不代表原生产 OpsLine 所有表天然是一条预约一行。
- 对源数据的历史与新增部分识别来源，避免错误地把同一业务事实重复纳入。
- 医生科室映射有开始与下一次调整日期，必须按事件时间识别当时有效的关系。
- 多值预约项目先拆分再匹配映射，不能粗糙 `LIKE` 后随意取一条。
- 无收费的预约仍可能对到访和初复诊统计产生影响，不能单纯以内连接消费明细定义母集。

**BillingLine（费用/项目）**

- 区分业务项目行、收费明细行、账单信息：付款多笔是业务上合理的“一对多”，需明确何时汇总、何时保留明细。
- 收费项目映射本身如有重复键，应先治理映射表或确立匹配优先级，不能依靠外层 `DISTINCT` 掩盖数据膨胀。
- 收费日期可能是高精度时间字符串、Excel 日期序列号或混合类型，接入时应区分错误输入与合法空值。
- 金额计算优先定义十进制定点精度；跨 BI 的数量取整需明确舍入模式。

### 为什么采用多阶段加工？

根据工作簿与血缘图可以确认：OpsLine/BillingLine 有连续的 DWD 加工节点。但每个阶段的真实任务**尚未由存储过程代码完整交叉验证**，所以不能编造“第 1 步做清洗、第 2 步做全部映射、第 3 步做金额汇总”的唯一正确步骤。公开仓库适合解释多阶段设计的价值：

1. 将不同的数据粒度和业务规则分开处理，便于检查 `JOIN` 前后的唯一性；
2. 对重复使用的中间计算形成稳定边界，降低下游重复计算；
3. 允许在各阶段验证记录数、缺失率和指标值，快速定位错误第一次出现的位置；
4. 通过依赖顺序编排，确保上游产生结果后再执行下游。

**建议后续根据真实存储过程补一张“阶段输入、输出、粒度、主要转换、检查点”表**，不要只在简历和 README 中出现模糊的“多阶段”。

## 4. 映射表建模：业务条件不能省

工作簿中的医生科室历史映射表（原内部表名已泛化，下文示例记作 `dim_staff_department`）存在“调整日期/下次调整日期”，属于典型的**带有效期的业务映射**。若直接 `JOIN` 当前最新科室，就会对历史预约产生错误回填。

正确的业务判断是事件时间位于映射有效区间：

```sql
-- 演示片段：并非生产 SQL；映射有效期约定为左闭右开
LEFT JOIN dim_staff_department AS d
  ON d.staff_key = e.staff_key
 AND e.event_at >= d.valid_from
 AND e.event_at <  d.valid_to;
```

依旧要验证同一个员工在某事件时间是否只匹配一条映射；若区间重叠，添加时间条件**仍会出现膨胀**。还应定义 `valid_to IS NULL` 的当前有效区间含义。

预约项目映射的另一类问题是业务单元格保存了由逗号分隔的多个项目名。`LIKE '%关键字%'` 会将相似项目误判为同一项目；应先拆分、标准化，再执行精确映射。如果业务要求“选择排序最前的科室”，除了排序值还应有确定的并列规则。

## 5. 粒度是避免 JOIN 数据膨胀的根本

| 数据集 | 假设粒度（须按生产字典确认） | 典型关系 | 可能出现的问题 |
|---|---|---|---|
| 预约事实 | 每次预约/行为 | 预约 → 多项目 | 关联项目后重复计算预约人次 |
| 收费事实 | 每笔收款/结算流水 | 一个业务订单 → 多笔付款 | 重复乘以业务项目行，金额膨胀 |
| 项目明细 | 每个订单项目 | 一个订单 → 多条收费明细 | 不应在订单未汇总时把明细和收费彼此直接 JOIN |
| 费用项目映射 | 每个业务有效映射键 | 一条项目 → 一条规则（理想） | 源映射重复导致本应 1:1 的 JOIN 变 1:N |
| 历史科室映射 | 人员 + 有效期 | 人员 → 多历史记录 | 未加时间窗口时错误关联最新科室 |

这个表是**建模复盘模板**；源文件并未证明每张源表的全部真实候选键。需要使用 `GROUP BY / COUNT(*)` 按实际字段确认。

## 7. 建模之后如何复核

1. 用已知业务事件构造小样本，明确预期结果（不使用客户真实记录）。
2. 对每个 `JOIN` 输出关联前后行数、自然键 distinct 数、重复计数。
3. 对“最早/最新/最大金额”类指标明确排序、边界和并列值规则。
4. 对有历史生效规则的映射，用变更日期前后各一条样例测试。
5. 复核从 DWD 到 ADS 的“是否丢失母集记录”和“是否重复放大金额”。
6. 最后与 BI 旧口径做分组织、日期与场景的结果比对，出现差异时区分**原 BI 逻辑缺陷**和**SQL 迁移缺陷**，不要一律强制复制旧缺陷。
