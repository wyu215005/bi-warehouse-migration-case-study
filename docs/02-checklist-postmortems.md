## 案例 A｜Excel 导入行数正确，字段却静默变为 NULL

**对应工作簿：Check List 第 2 行**

**现象**：SSIS 从 Excel 导入 SQL Server 后，表总行数对得上，部分应有内容的日期、年月或分类字段却出现大量 `NULL`。

**根因**：Excel 驱动可能只抽样前若干行推测列类型；默认典型值为前 8 行，但受 `TypeGuessRows`、提供程序、位数与连接设置影响，不是 SQL Server “任何情况下只读前八行”的固定机制。若同列混有文本和数字，某些值会被驱动解释成空值。

**源记录中的处理方式**：针对缺失值严重的表，采用 Python 导入脚本，避免盲目信任 Excel 驱动的类型推断。

**复盘要点**：

- 不只看 `COUNT(*)`，还要逐列检查源值非空数与目标非空数。
- 导入字符串、日期、金额时显式定义读取与规范化策略。
- 采用 `IMEX=1` 等设置也需要真实样本验证，不能保证任何 Excel 都自动解决。
- 字段一旦在 ODS 丢失，DWD 再高级的计算也无法找回它。

**回归样例**：前八行全为整数、第九行为包含字母的编码；源端第九行必须在 ODS 完整保留。

## 案例 B｜合并单元格导致录入时间缺失

**对应：第 3 行**

**现象**：源 Excel 中一个合并单元格覆盖多行数据，导入后只有合并区域第一个逻辑单元格存在值，后续行为空。

**源记录处理方式**：使用 Python 脚本进行展开/填充后入库。

**关键边界**：不能无条件对整列 `ffill`。需要先确认该列是否确为**同一合并区域对应的属性**，且填充值不会跨患者、单据、文件或业务分组。最佳方式是读取实际合并区域信息，在区域内恢复其原始共享值。

**核验**：合并区域的行数是否与展开后的非空记录一一对应，非合并区域空值是否仍保留。

## 案例 C｜错误 JOIN 键引发上百万行数据膨胀与 TempDB 耗尽

**对应：第 4、8、9 行**

**现象**：预约主线首次 DWD 大规模加工时发生 TempDB `PRIMARY` 文件组空间不足。记录显示当时主数据约 280 万行，多个临时表围绕主表反复 `LEFT JOIN`；部分关联使用了由“组织 + 病历标识”组成、但无法唯一标识一条预约事件的键。

**分析**：

- 当左侧某键匹配右侧 N 条记录时，输出数据会由 1 行变为 N 行。
- 业务主体键（如患者 + 门店）并不等价于预约事件键。
- 如果放大后又经过多轮临时表 JOIN、排序、`SELECT INTO`，可能消耗大量 TempDB；但“文件组已满”也与磁盘容量、增长限制、执行计划、索引和并发有关，不能只凭现象断言唯一原因。

**工作簿记录的改法**：将一些使用宽泛业务 KEY 关联的逻辑，调整为与预约事件更接近的复合键（记录中包含预约时间、预约编号、来源等）。

**更严格的工程解释**：**复合字段看起来更细并不等于已经证明唯一**。还应检查 `NULL`、重号和同一时间事件冲突：

```sql
-- 示例：请根据真实业务事件键替换名称；不是生产查询
SELECT source_system, appointment_id, event_at, COUNT(*) AS duplicate_count
FROM dbo.sample_appointment
GROUP BY source_system, appointment_id, event_at
HAVING COUNT(*) > 1;
```

并比较各个中间阶段的 `COUNT(*)`、自然键去重数、执行计划、TempDB 使用量。没有这类数据，不能在简历写“性能提升 80%”。

## 案例 D｜映射表存在重复业务键，导致费用记录膨胀

**对应：第 4、9、14 行**

**现象**：费用项目主题关联收费项目映射时，映射表中同一个项目名存在多条匹配记录；关联后的项目/金额记录增加。

**源记录做法**：在前置临时表处理映射键重复，对关联的目标关系作唯一化处理。

**复盘**：

1. `ROW_NUMBER` 去重前要先明确定义“同键的多版本中选择哪一个”，不能任意丢弃合法规则。
2. 使用 `DISTINCT` 隐藏输出重复，会掩盖映射规则冲突。
3. 如果映射键包含全/半角、括号、空格或不同 Collation，应先设计可控的**标准化键**。
4. 即便 `JOIN` 后记录数与源表一致，也要检查非空项目被映射到哪个分类。

## 案例 E｜历史科室被最新维度值覆盖

**对应：第 6 行**

**现象**：历史预约关联医生科室信息时，错误地使用最新科室覆盖了当时的科室，导致历史运营分组数据被污染。

**根因**：映射关系具有生效时间，原 SQL 未按业务事件时间限制规则区间。

**工作簿中的处理方法**：按员工映射及 `[生效开始] <= [预约时间] < [下一次生效]` 匹配历史数据。

```sql
-- 模拟字段，不含真实员工数据
LEFT JOIN dim_staff_department AS h
  ON e.staff_key = h.staff_key
 AND e.appointment_at >= h.effective_from
 AND e.appointment_at <  h.effective_to;
```

**核验**：在科室变更前/后各构造一条预约；同一预约最多匹配一个有效映射；区间边界及空结束时间应有单独规则。

**迁移价值**：这是时间有效维度（Type 2 / 有效期映射）的业务思想，与 SQL Server、Hive 或 Spark 使用何种引擎无关。

## 案例 F｜多值预约项目用 LIKE 模糊匹配，导致错误科室

**对应：第 7、18、20 行**

**现象**：业务源用逗号分隔多个项目名，原 SQL 用 `LIKE` 模糊匹配，可能将相似名称当成同一个项目；源项目左侧空格等脏值又会让精确匹配失败，最终部分科室为 NULL，影响到访量分组。

**工作簿记录的处理**：使用 `STRING_SPLIT` 拆分、`LTRIM/RTRIM` 去首尾空格、与项目映射精确关联，并通过 `ROW_NUMBER` 对同一预约取业务排序优先的科室。

**进一步改进**：

- `STRING_SPLIT` 分隔符必须符合实际格式（中英文逗号、空白、特殊符号），不能假设所有文件用同一分隔符。
- 同一排序值若存在多个候选规则，应增加稳定且有业务含义的第二排序键。
- 未匹配到映射时应输出“未知/待维护”及告警，不应静默丢失预约事实。
- 执行 `STRING_SPLIT` 之前先确认目标业务是否真的允许同一预约对应多个项目及多个科室。

## 案例 G｜日期字符串带七位小数秒，转换 DATETIME 失败

**对应：第 10、16 行**

**现象**：收费日期及初诊日期字段部分转换成日期失败或落为 NULL。源值示意：`2025-08-07 11:23:00.0000000`。

**根因**：SQL Server `datetime` 不支持 `datetime2(7)` 所能表达的全部小数秒精度；不能把任意七位小数秒字符串都视作可安全直接转为 `datetime`。

**记录处理**：先转换为 `datetime2` 后按业务需求再提取 `date`、月份；只有确有必要时才转换较低精度的 `datetime`。

```sql
-- 合成示例
DECLARE @raw nvarchar(40) = N'2025-08-07 11:23:00.0000000';
SELECT TRY_CONVERT(datetime2(7), @raw) AS parsed_timestamp,
       CAST(TRY_CONVERT(datetime2(7), @raw) AS date) AS business_date;
```

**可复现事实**（2026-10-17 于本地 SQL Server Developer 实例 v17.0 实测）：

- `TRY_CONVERT(datetime, N'2025-08-07 11:23:00.0000000')` 与 `TRY_CONVERT(datetime, N'2025-08-07 11:23:00.1234567')` 均返回 `NULL`——字符串小数秒位数超过 3 位时，直接转 `datetime` 解析失败；
- `TRY_CONVERT(datetime2(7), 同值)` 解析成功；先转 `datetime2(7)` 再 `CAST` 为 `datetime` 亦成功（小数秒按四舍五入进位，`.9999999` 会进位到下一秒）。

该行为与 Check List 记录的现象一致，是独立于旧记录、可在测试实例复现的技术事实；具体边界随 SQL Server 版本与转换样式可能不同，迁移前应使用真实格式样本在目标实例验证。

**注意**：若业务要求精度，则存储为 `datetime2(7)` 比多做一次降精度转换更合理；`TRY_CONVERT` 返回 NULL 仍需记录坏值和处理规则。

**对应：第 19 行**

**现象**：同一天多次转诊记录都被识别为复诊。

## 案例 M｜金额在 Python → ODBC → SQL Server 之间发生精度变化

**对应：第 22 行**

**现象**：源金额与迁移后部分金额出现精度或尾数差异，进而影响最大消费、相等比较及分类判断。

**工作簿记录的怀疑链条**：Excel 数值被 pandas/Python 读入后，经 ODBC 参数绑定和 SQL Server 字符隐式转换，精度或格式发生变化；后续对金额列使用专门清洗、字符串格式化逻辑进行修复。

**注意科学性**：工作簿的“浮点读取精度无损”“SQL Server 一律只保留六位有效数字”等表述过于绝对；这些行为依赖具体读取方式、参数类型、目标字段类型和转化路径，需要原始值/参数类型/写入值三点逐项验证。

**推荐原则**：在金额业务规则明确时，尽量以合适精度的 `DECIMAL(p,s)` 处理，并避免将非精确的浮点值作为金额等值比较依据。数据类型选型和舍入需要业务确认，而非任意定标。

## 案例 O｜整数转换：四舍五入和银行家舍入不是一回事

**对应：第 24 行**

**现象**：数量字段在 BI 中转换为整数后的结果，与 SQL Server `ROUND`/`CAST` 的输出不一致。

**工作簿提到** Power Query 的 `Int64.From` 默认 `RoundingMode.ToEven`（向最近偶数舍入），而 SQL Server 的 `ROUND` 对中间值处理语义可能不同。

**示例边界**：`0.5→0`、`1.5→2`、`2.5→2`、`-1.5→-2`。应区分原模型实际用的是 DAX `ROUND`、Power Query `Number.Round`、`Int64.From` 还是强制类型转换，不能笼统称“DAX 一律采用银行家舍入”。

**三种舍入语义实测对照**（T-SQL 部分于 2026-10-17 在本地 SQL Server Developer 实例实测；`Int64.From` 为 Power Query 文档语义）：

| 输入 | T-SQL `ROUND(x,0)` | T-SQL `CAST(x AS int)` | Power Query `Int64.From`（ToEven） |
|---:|---:|---:|---:|
| 0.5 | 1 | 0 | 0 |
| 1.5 | 2 | 1 | 2 |
| 2.5 | 3 | 2 | 2 |
| -0.5 | -1 | 0 | 0 |
| -1.5 | -2 | -1 | -2 |
| -2.5 | -3 | -2 | -2 |

结论：T-SQL `ROUND` 是“四舍五入、`.5` 远离零”；`CAST` 到整数是“向零截断”；`Int64.From` 是“向最近偶数”。三者互不相同，跨工具迁移数量口径时必须先确认源端实际使用的是哪一种。

**注意**：工作簿记录了一个候选 `CASE` 实现，但未提供覆盖正负数和所有 `.5` 边界的测试结果；公开示例应先编写测试用例，再确定 SQL 等价表达式。

参考：[Microsoft Learn - Int64.From](https://learn.microsoft.com/en-us/powerquery-m/int64-from)。

## 案例 P｜尚未闭环的指标差异

**对应：第 5、11、21 行等**

- **相同业务信息但不同账单号时为何取最大账单号？** 原记录给出“MAX/MIN 稳定取一”的解释，但**值稳定不等于业务选择正确**。必须先定义账单号排序是否真的表达最新、优先或代表性。
- **转介行为全被判为“无转介”**：记录没有确认原因和修复过程；不能据此宣称已解决。

这几个问题适合继续做深：保留原始错误、设计期望样例、给出最终验证结果。**主动承认尚未闭环，比写不出证据的“全部修复成功”更专业。**

```text
经验：能迁移到另一种数据引擎的原则是什么
```

## 结论：可迁移的是方法，不是 T-SQL 语法

这些问题的共同点是：需要先定义**业务母集、粒度、关联基数、时间有效期、精度和筛选语义**。将来换成 Spark SQL、Hive SQL 或其他 ETL 工具，函数和执行机制会变化，但业务正确性验证方法依然成立。
