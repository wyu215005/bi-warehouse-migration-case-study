# 04｜数据质量：从技术校验到 BI 业务验收

> **资料来源**：Excel“Check List”“BI同步进度表”，以及既有项目对账实践讨论。文中的核验规则是**以项目实际问题为基础整理的完整测试方法**；未提供生产日志的规则，属于建议测试，不代表当时已经做过全部自动化质量门禁。

## 1. 为什么行数一致不等于迁移成功

可以构造两种极端情况：

1. 源文件第 9 行的字符串编码无法被 Excel 驱动按前几行推断的数据类型解析；该行依然插入，但关键列变为 NULL。**源、目标 `COUNT(*)` 一致，值已丢失。**
2. 一条收费流水被不唯一的映射表复制为两条，即使后来某条记录被错误过滤，最终总行数也可能碰巧相等。**总行数一致，指标仍可能错误。**

所以需要把校验分成五层，而不是只比较表数量和数据总行数。

## 2. 五层质量检查

| 层级 | 验证什么 | 例子 | 检查失败时的下一步 |
|---|---|---|---|
| 文件/接入 | 文件、记录与字段读取完整性 | Excel 非空字段 → ODS 非空字段 | 源驱动类型推断、合并单元格、日期序列号 |
| 明细/粒度 | 一行代表什么、候选键是否唯一 | `source + appointment_id + event_time` 分组 | 判断自然键与业务母集是否定义错误 |
| 规则/映射 | 规范值、有效期、业务优先级 | 预约时的医生科室是否正确 | 时间区间、编码清洗、映射重复 |
| 汇总/指标 | 人次、数量、金额、首次/最近口径 | 月份 × 分院 × 科室 | 业务过滤、分组、连接基数、舍入 |
| BI/交付 | 新旧数据源表现一致或差异有解释 | Power BI 换源前后的指标对账 | 区分迁移 Bug 与原报表历史缺陷 |

## 3. 质量关卡定义：先明确预期，不是只会写断言

### Q1. 非空与类型一致

- 关键列：源端非空值进入 ODS 后不应静默丢失；
- 日期：解析失败必须区分真实缺失和格式错误；
- 金额：采用确认过的 `DECIMAL(p,s)` 及舍入模式，不能只比较浮点展示值；
- 文字：必要时同时比较原始文本、规范化文本与分类映射结果。

### Q2. 连接前后一致性

对每个重要 `LEFT JOIN`，至少确认：

- 主表候选键有无重复？
- 右表关联键是否应唯一？实际重复多少次？
- 原主表有多少行未匹配？
- 连接后是否超过允许的业务粒度变化？
- 若右表允许多行，是否先按业务规则聚合/排序？

**关键区分**：合法的“一订单多次付款”不是需要删除的脏数据；但“一订单多次付款”和“一订单多条项目”直接交叉 JOIN，可能造成乘法放大。

### Q3. 历史有效性

如果科室、医生归属、项目分类在历史时间发生变化：

- 事件发生在变更前，匹配旧归属；
- 事件发生在变更后，匹配新归属；
- 有效区间是否重叠？
- 未知/空结束日期如何处理？
- 与原 BI 的历史逻辑是否一致？

### Q4. 业务指标与上下文

重点验证的场景：

- 首次/最近到访日期、同一天多次预约；
- 初复诊判断、无收费但存在预约的业务记录；
- 项目收费可能分多笔完成；
- 收费项目映射多个候选分类；
- 日期时间字符串带七位小数秒；
- 金额相等比较、数量向偶数舍入。

### Q5. 换源验收

采用“总览 → 分组 → 明细”的逐级对账：

1. 按统计月份比对总体记录数、到访量与收款金额；
2. 按组织、科室、业务类别深入分组；
3. 对差异最大的组，筛选出候选业务键/时间窗口；
4. 沿 ADS → DWS/DWD → ODS 逐层排查；
5. 若原 BI 逻辑本身有缺陷，记录“差异合理的业务原因”，而不是强制制造同样的旧错误；
6. 在发布/交付时保存差异清单、处理状态与结论。

> 项目既有交流证实做过月度、分院、到诊/收费等多角度对账与 Power BI 换源验证；但当前资料没有“118 张输出表逐表最终验收结果”的完整原始日志，因此公开版不写“100% 精确一致”。

## 5. 构造小样本测试矩阵

将真实问题抽象为不含患者信息的边界样例：

| 编号 | 模拟输入 | 期望结果 | 对应真实案例 |
|---|---|---|---|
| T01 | 8 行数值 + 第 9 行混合文本 | 全部非空值仍被读取 | Excel 类型推断 |
| T02 | 两行共用一个 Excel 合并单元格 | 只对同一合并区域正确恢复共享值 | 合并单元格 |
| T03 | 同一预约键在项目映射中匹配两行 | 不无故复制预约事实 | 映射重复 |
| T04 | 一个订单有 2 项目、2 笔独立付款 | 项目总额/收款总额不被 2×2 放大 | 不同事实粒度 |
| T05 | 员工调换科室前后各一条事件 | 两条事件归属不同科室 | 历史维度 |
| T06 | 项目值 `检查,复查` 与映射值 `检查` | 以拆分后精确匹配为准 | LIKE 误匹配 |
| T07 | `2025-08-07 11:23:00.0000000` | 按 DATETIME2 正确解析 | 日期精度 |
| T08 | 0.5、1.5、2.5、-1.5 | 按明确规则验证舍入结果 | Power Query 口径 |
| T09 | 有预约但从无消费 | 不被不合理提前过滤 | 初复诊统计 |
| T10 | 最近日期存在同日两条事件 | 按约定 tie-breaker 决定结果 | DAX 上下文还原 |

本仓库的 `examples/synthetic_checks.sql` 提供了其中一部分**基于模拟数据的可执行断言**。文件无需生产数据库表，只会使用 SQL Server 临时表/局部变量；实际运行前仍建议先在独立的测试环境检查。

## 6. 与“运行成功”分离的交付定义

建议验收时把两个状态拆开：

- **技术运行成功**：包/过程结束状态成功，无 SQL 异常；
- **业务数据通过验收**：核心指标、时间口径、映射和边界样例符合预期，BI 换源差异有记录。

“批次成功”和“业务正确”是两件事。如果业务核验没有通过，就算调度全部显示绿色也不应直接完成交付。
