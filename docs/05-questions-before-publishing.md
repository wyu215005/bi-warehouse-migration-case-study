## 四、深度补完任务

### 阶段 1：业务结构

- 画出预约、项目、订单、收费流水、映射维度的**粒度关系图**；
- 写出 3 个真实业务指标的业务定义、分组粒度、边界案例；
- 明确 S01/S02 的实际业务粒度与复合候选键。

### 阶段 2：加工链路

- 从两条主线中各选一个复杂业务字段；
- 用“原 BI 规则（可改写为伪代码）→ 输入数据 → SQL 加工思想 → 测试数据 → 预期输出”解释；
- 按阶段记录表数量、字段数量的变化与粒度是否变化，不一定公布真实生产指标。

### 阶段 3：运行与验收

- 绘制真实的 17 批次依赖示意（可脱敏、简化）；
- 选一次典型批次失败，按时间线复盘；
- 设计数据质量测试矩阵并使用模拟数据运行，提供结果截图。

### 阶段 4：血缘与衍生项目

- 基于模拟表及过程关系，生成不含企业字段的血缘 JSON；
- 若有精力，可把现有静态工具重构为可复用的**匿名示例**；
- 未来学习 Spark/Hive 后独立完成新版本，明确标注为个人学习扩展而非原实习生产栈。

## 五、准备面试时的自检提纲

**90 秒口头框架**：背景为何需要迁移 → 你负责哪些步骤 → 什么业务复杂度使简单 SQL 翻译不可行 → 怎样拆层/确认粒度 → 如何在 ETL 批次中保证前后依赖 → 怎样核验 BI 指标 → 一个解决过的故障与思考。

面试官若进一步追问，重点准备回答：

1. S01 / S02 的粒度和业务键到底是什么？
2. 同一个订单两笔收款如何避免 JOIN 后重复计算？
3. 历史医生科室映射为什么不能取最新维度？
4. `ROW_NUMBER` 选中的那一条业务记录，排序依据是什么？
5. 什么时候 `LEFT JOIN` 是错误的？什么时候 `INNER JOIN` 会丢失业务母集？
6. Check List 中哪个故障导致你真正改变了建模或排错思路？
7. 日增量如何覆盖历史记录更新？如果不能，如何给使用方说明边界？
8. 静态血缘图更新不及时，会有哪些风险？

每个回答都应给出明确前提或样例，不用背空泛的“最优实践”。
